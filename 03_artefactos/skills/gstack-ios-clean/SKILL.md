# gstack-ios-clean — Limpieza de un paquete de instrumentación de debug en iOS

## Cuándo invocar esta skill

Invócala cuando un proyecto Swift/iOS deba eliminar un paquete de
instrumentación de depuración (típicamente un paquete SPM de diagnóstico o
debug bridge) junto con todo su cableado de compilación condicional. La skill
cubre los tres síntomas habituales: dependencias SPM de debug en
`Package.swift`, bloques `#if DEBUG` que arrancan el bridge en el `@main`, y
archivos generados por el paquete que quedaron huérfanos en el árbol de
fuentes.

Es la pieza opuesta a una limpieza a mano sin orden: en lugar de borrar
archivos y rezar que el build pase, la skill audita referencias, describe el
plan de remoción, y solo después de confirmación explícita del usuario ejecuta
los edits.

## Principio de la capability

La capability **no edita archivos por sí sola**. Es una skill de evaluación
local fail-closed: lee el manifiesto y las fuentes, produce un inventario de
referencias a remover, y presenta el plan al usuario. La ejecución de los
edits requiere confirmación explícita puerta por puerta. Sin confirmación, no
hay mutación.

Esto protege contra la clase de fallo más común en limpiezas de debug: borrar
la dependencia SPM pero dejar un `#if DEBUG` colgando que el compilador de
Release acepta silenciosamente (porque la rama no compila) y el de Debug
rechaza de forma críptica. La skill hace el inventario antes de tocar nada.

## Qué remueve

Cada ítem se revierte solo después de confirmación puerta por puerta:

1. La entrada del paquete de debug en `Package.swift` (`.package(...)` y
   cualquier target que lo referencie en `dependencies:`).
2. Los bloques `#if DEBUG` del `@main` de la app que invocan al manager del
   bridge (ej. `DebugBridgeManager.shared.start()` o equivalente).
3. Los `import` del paquete de debug dispersos en fuentes.
4. Archivos generados por el paquete (ej. accessors de estado, snapshots
   helpers) que queden huérfanos tras remover el import.
5. Tokens o markers temporales del paquete en `NSTemporaryDirectory()` del
   device (best-effort: solo si el device está conectado).

## Qué NO toca

- Lógica de negocio, view models, código de vistas.
- Cualquier cosa fuera de bloques `#if DEBUG`.
- Otra infraestructura de test o QA no relacionada al paquete de debug.
- El caché SPM; eso es decisión del usuario.

## Fase 1: Inventario

1. Grep por `import <DebugModule>` en todo el árbol de fuentes de la app.
2. Grep por `#if DEBUG` blocks que referencian al manager del bridge.
3. Grep por markers de código generado del paquete (headers tipo
   `// Auto-generated by <DebugModule>` o similares).
4. Parsear `Package.swift` para la entrada de dependencia del paquete de debug.
5. Mostrar al usuario el inventario: archivos, line counts, y bloque exacto a
   remover por cada uno. Pregunta: proceder, dry-run, o abortar.

## Fase 2: Remover

Por cada ítem que el usuario aprobó (puerta por puerta):

1. Edit para remover el `import` y el bloque `#if DEBUG` (preservar el código
   circundante intacto).
2. Edit para remover la entrada `.package(...)` de `Package.swift` y cualquier
   target que liste el paquete en `dependencies:`.
3. Borrar los archivos generados huérfanos identificados en la Fase 1.
4. Correr `swift build -c release` (o `xcodebuild -scheme <Scheme> -configuration
Release build`) para verificar que Release compila sin el paquete. Si falla
   por un símbolo faltante del bridge, la remoción quedó incompleta: STOP y
   reportar.

## Fase 3: Verificar

1. `grep -r "<DebugModule>" <app-source-dir>` → sin matches.
2. `grep -r "#if DEBUG" <app-source-dir> | grep -i <DebugModule>` → sin
   matches.
3. `swift build -c release` pasa.
4. `nm` sobre el binario compilado no muestra símbolos del paquete de debug.

Reportar el resultado + una línea de resumen de qué se removió.

## Reversibilidad

Cada Edit y delete es una operación git; el usuario puede `git restore` para
revertir. La skill nunca hace force-push, nunca amenda, nunca borra el caché
SPM. Esas son decisiones del usuario.

## Fail-closed

Sin write-set declarado y confirmación explícita del usuario, la skill no
edita. Una ausencia no se sustituye por una inferencia. Si el inventario
encuentra referencias ambiguas (ej. `#if DEBUG` que mezcla el bridge con
otra instrumentación), marca `coverage_gap` y pide al usuario que delimite
antes de proseguir.
