# gstack-ios-sync — Resincronización de una capa de instrumentación generada

## Cuándo invocar esta skill

Invócala cuando un proyecto deba regenerar una capa de código generado por
templates (típicamente un debug bridge, un set de accessors tipados, o una
capa de instrumentación derivada de templates upstream) contra la versión
más reciente de esos templates. La skill cubre los tres síntomas habituales:
los templates upstream cambiaron y la capa generada local quedó desfasada, se
añadieron al proyecto nuevas entidades marcadas que requieren cobertura de
accessors, o los markers del generador (comentarios tipo `// @Snapshotable`
o equivalentes) se movieron a otros campos.

Es la pieza opuesta a una regeneración a ciegas: en lugar de sobrescribir los
archivos generados y rezar que las customizaciones se conserven, la skill
diffea templates, identifica qué customizaciones locales existen, y solo
después de confirmación explícita del usuario ejecuta la regeneración.

## Principio de la capability

La capability **no regenera archivos por sí sola**. Es una skill de
evaluación local fail-closed: lee los templates upstream y la capa generada
local, diffea, clasifica las customizaciones locales, y presenta al usuario
el plan de merge antes de regenerar. La ejecución del regenerator requiere
confirmación explícita. Sin confirmación, no hay mutación.

Esto protege contra la clase de fallo más común en resincronizaciones de
código generado: el generador sobrescribe archivos generados y borra
silenciosamente las customizaciones locales (hand-rolled accessors, hooks
de testing, overrides de serialización) que el equipo añadió encima de la
capa generada. La skill hace el diff y el inventario de customizaciones
antes de tocar nada.

## Qué hace

Cada fase se ejecuta solo después de confirmación puerta por puerta:

1. Diff entre templates upstream y la capa generada local.
2. Identificación de customizaciones locales (ediciones manuales sobre
   archivos generados, markers movidos, hooks añadidos).
3. Estrategia de merge: decidir qué customizaciones se preservan, cuáles se
   descartan porque el template las resuelve upstream, y cuáles requieren
   migración manual.
4. Regeneración: correr el generador determinístico una sola vez, con la
   configuración de merge aprobada.
5. Verificación: el build pasa, los accessors nuevos cubren las entidades
   marcadas, el schema hash refleja el cambio.

## Qué NO toca

- Lógica de negocio, view models, código de vistas.
- Archivos handwritten del proyecto (solo la capa generada y los markers).
- El caché del generador; eso es decisión del usuario.
- Otra infraestructura de test o QA no relacionada a la capa generada.

## Fase 1: Detección de versión instalada

1. Leer el marker de versión instalada (escrito por el instalador del
   paquete en un archivo tipo `.version` o equivalente dentro de la capa
   generada). Si falta, tratar la instalación como "versión antigua
   desconocida".
2. Leer la versión upstream desde el root del paquete de templates.
3. Si las versiones coinciden Y no se añadieron nuevas entidades marcadas
   desde la última regeneración, salir temprano con "ya actualizado".

## Fase 2: Diff de templates y customizaciones

1. Diff entre los templates upstream actuales y la capa generada local:
   qué archivos cambiaron, qué se añadió, qué se removió.
2. Identificar customizaciones locales: grep por headers de código generado
   (`// Auto-generated by ...` o equivalentes) en archivos que también
   contienen ediciones manuales, grep por markers del generador movidos,
   grep por hooks de testing o overrides de serialización añadidos sobre la
   capa generada.
3. Clasificar cada customización: preservar (el template no la resuelve),
   descartar (el template la resuelve upstream), migrar manualmente (requiere
   edición humana post-regeneración).
4. Mostrar al usuario el diff + el inventario de customizaciones clasificadas.
   Pregunta: proceder con la estrategia de merge, dry-run, o abortar.

## Fase 3: Regenerar

Por cada ítem que el usuario aprobó (puerta por puerta):

1. Correr el generador determinístico una sola vez, con la configuración de
   merge aprobada. El generador debe aceptar el directorio de fuentes a
   escanear y el directorio de la capa generada a escribir.
2. Confirmar que el generador no modificó archivos handwritten del
   proyecto; solo la capa generada.
3. Migrar manualmente las customizaciones clasificadas como "migrar
   manualmente": edición humana post-regeneración, re-aplicando el hook u
   override sobre el archivo recién generado.
4. Si el generador reporta un marcado inválido (entidad no soportada, tipo
   rechazado, marker en campo no escaneable): STOP, no sobrescribir, y
   reportar al usuario.

## Fase 4: Verificar

1. El build del paquete pasa (`swift build` o equivalente).
2. El build del esquema de la app pasa (`xcodebuild -scheme <Scheme>` o
   equivalente).
3. Re-lanzar la app; la capa de instrumentación conecta + rota token (si
   aplica).
4. El endpoint o accessor de snapshot devuelve el nuevo schema hash (si
   aplica).
5. Grep de customizaciones preservadas: cada hook u override clasificado
   como "preservar" sigue presente en la capa regenerada.

Reportar el resultado + una línea de resumen de qué se regeneró y qué
customizaciones se migraron.

## Reversibilidad

Cada regeneración es una operación git; el usuario puede `git restore` para
revertir. La skill nunca hace force-push, nunca amenda, nunca borra el
caché del generador. Esas son decisiones del usuario.

## Fail-closed

Sin write-set declarado y confirmación explícita del usuario, la skill no
regenera. Una ausencia no se sustituye por una inferencia. Si el diff
encuentra customizaciones ambiguas (ej. edición manual que no se puede
clasificar como preservar o descartar sin criterio humano), marca
`coverage_gap` y pide al usuario que delimite antes de proseguir.
