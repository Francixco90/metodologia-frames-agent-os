# Abstract

S08 makes a hypothesis observable before major commitment. A sketch organizes a concept; a prototype lets people encounter behavior; neither is a validated product or production system. [METODOLOGIA][source_ref:NFC-DRV-S08]

</abstract>

<knowledge>

# Prerequisites and concepts

Prerequisite: problem, intended user, existing evidence, and one decision the test can change. Concepts: assumption, hypothesis, sketch, prototype, pilot, system; fidelity versus learning value; discovery; information architecture; Definition of Done; feedback and stop/iterate/advance rules.

# Sequence

State problem and evidence. Ask no more than a focused round of discovery questions. Register assumptions and risks. Choose the lowest-cost representation able to test the riskiest assumption. Run with a representative user or realistic proxy. Capture behavior and feedback. Decide stop, iterate, or advance.

# Misconceptions

A polished render validates demand; the tool is the solution; prototypes must succeed; a functional mini-app is production-ready; assumptions disappear behind a professional interface.

# Practice and transfer

Produce a canvas, sketch, and one functional path only if each changes what can be learned. Transfer by choosing a different idea and defending a smaller test than the initially requested build. [PEDAGOGIA]

</knowledge>
<evidence>

# Evidence

Expected evidence: hypothesis, risk ranking, representation choice, participant/proxy, observations, decision rule, and outcome.

</evidence>
<decisions>

# Decisions

Optimize fidelity for the question, not visual impressiveness. A useful test must be able to disconfirm the hypothesis.

</decisions>
<assumptions>

# Assumptions

[SUPUESTO] Feedback can be collected ethically and without exposing sensitive data.

</assumptions>
<limits>

# Limits

Prototype evidence is local to the tested user, task, and conditions; it does not prove scale, security, adoption, or ROI.

</limits>
<edge_cases>

# Edge cases

If no representative user is available, label proxy evidence. If the interface itself is not the risk, test the service or workflow instead. If failure can harm, simulate.

</edge_cases>
<acceptance>

# Acceptance

The learner selects the smallest valid representation, runs a refutable test, distinguishes observation from interpretation, and makes an explicit stop/iterate/advance decision. [PEDAGOGIA]

</acceptance>
